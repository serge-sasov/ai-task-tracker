# C1 brief: Backend — ordered `models` field and TaskQueryService tests

## Goal
Derive an immutable, ordered `models` list on the task-list DTO from the same
`token_usage` rows used for `tokens_total`, and add unit tests for ordering,
tie-break and empty-usage.

## Inputs (path + line range, read only what is needed)
- DTO to change: `src/main/java/ru/aitasktracker/api/dto/TaskListItem.java`
  (lines 1–57): add `List<String> models` (defensive copy). Keep the existing
  7-arg constructor; add a second constructor taking `(taskId, name, startedAt,
  finishedAt, status, durationS, tokensTotal, models)`.
- Service: `src/main/java/ru/aitasktracker/api/service/TaskQueryService.java`
  (lines 114–136): `toListItem` must compute `models` from ONE
  `tokenUsageRepository.findByTaskId(taskId)` call shared with `tokensTotal`,
  not a second call per task.
- Test: `tests/java/ru/aitasktracker/api/service/TaskQueryServiceTest.java`
  (add new methods using the existing Mockito style/mocks).
- Ordering contract (contracts §4.2, architecture class CLS-001/CLS-002): total
  tokens = input+output+cache summed per model; order by that total descending,
  then model name ascending for ties; no usage → empty list.

## Implementation notes
- Aggregate per model: sum input+output+cache across all rows of that `model`,
  ignoring `scope`/`message_id` (do NOT dedupe by scope).
- Compute `models` in the same call site as `tokens_total`: fetch rows once,
  compute the grand total AND the per-model totals, then build the ordered
  model list. Do not call `findByTaskId` twice for the same task in `list()`.
- Return an immutable `List<String>` via `Collections.unmodifiableList(...)`.
- Keep `tokens_total` behavior exactly as before (already input+output+cache).

## Tests to add (TaskQueryServiceTest, existing style)
- multi-model ordering: task with several models whose per-model totals differ
  → `item.getModels()` in descending-total order.
- tie-break by name: two models with equal total → ascending name order.
- empty usage: task with no `token_usage` rows → `getModels()` is empty.
- cache included in total: two rows same model differing in cache → cache counted
  in the per-model total that drives ordering.
- Defensive copy: mutating the returned list must not affect internal state.

## Acceptance
- `TaskListItem.models` ordered total-tokens desc / name asc; empty when no usage;
  reuses the existing `token_usage` rows (one `findByTaskId` per task in `list()`).
- Unit tests cover ordering, ties, empty, cache.
- `mvn -f backend/pom.xml test` passes.
