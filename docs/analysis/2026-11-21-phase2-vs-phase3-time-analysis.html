Короткий ответ

  • Рост не из-за retries, числа chunk’ов или объёма выдачи. Chunk’ов почти столько же (16 → 15), попыток по одной на chunk, produced-файлов даже меньше (38 → 31).
  • Главный драйвер — scope/complexity S-04. Day-view, month/year-календарь, общий ModelCell, built-frontend e2e и больше cross-cutting артефактов. Это видно по chunk titles и по U-02/R-01/R-02/I-01.
  • Второй драйвер — контекст и сессии. Brief-файлы выросли с 4 625 до 34 643 B; у R/I-задач input/cache/сессии в 4–7× выше.
  • Третий драйвер — verification/re-render/build/test. SVG re-render, OpenAPI re-validation, class/components/sequence diagrams, package-lock/vitest/build.
  • Review waits усилили календарный разрыв: 1 ч 02 мин → 26 ч 25 мин; T-036 — 13 ч 37 мин, T-032 — 8 ч.
  • Осторожно с U-02: 5 мин Phase 2 — outlier быстрого delta; ratio 45.8× чувствителен к этой базе.

Почему выросло время: ранжированные причины

Причины упорядочены по силе evidence. Это observational comparison: scope S-04 отличается по дизайну, а не случайно.

1

Scope и сложность S-04

S-04 — не «ещё одна колонка», а новое day-view с month/year-календарём, общим ModelCell и built-frontend e2e. S-01 был меньшим delta к существующему списку.

  • T-033: wireframes + SVG re-render, UI spec, prototype day table.
  • T-034: ADR shared model-cell + components + SVG + SCN-009 + SVG.
  • T-035: ModelCell CLS-005 + class diagram + OpenAPI re-validation.
  • T-036: shared ModelCell + S-01/S-04 integration + 8 файлов incl package-lock/vitest.
2

Контекст, briefs и сессии

Brief-файлы выросли 4 625 → 34 643 B; роли Phase 3 читали больше артефактов и работали в большем числе сессий.

  • T-034: 5 сессий, 377 315 input, 8 246 608 cache.
  • T-036: 7 сессий, 540 747 input, 9 652 968 cache.
  • Phase 2 T-022: 1 сессия, 48 057 input, 272 822 cache.
3

Verification / re-render / build

Phase 3 добавил проверки, которые не видны в diff: SVG re-render, OpenAPI re-validation, cross-check components/class/sequence, built-frontend и frontend build/test.

  • T-033-c2 и T-034-c2/c3 — явные SVG re-render шаги.
  • T-035-c3 — OpenAPI re-validation.
  • T-036 — package-lock/vitest/build, 8 produced файлов.
  • T-037 — built-frontend DOM smoke (in progress) — ещё впереди.
4

Rework и check-design gaps

Часть времени ушла на переоткрытие/сужение scope и ложные budget FAIL, а не на новую функциональность.

  • T-029: previous orchestrator session cancelled; 18 файлов / 885 строк snapshot.
  • T-033: budget corrected to U-02 norm; ISSUE-20261120-113748.
  • T-036: scope narrowing + chunk-budget FAIL (ISSUE-20261121-005209, ISSUE-20261120-113748); known check-design gap.
5

Review waits и календарные паузы

Work time и calendar time — разные вещи. Phase 3 review waits выросли с 1 ч 02 мин до 26 ч 25 мин; это объясняет большую часть calendar gap.

  • T-036: CP-1 13 ч 37 мин.
  • T-032: CP-F 8 ч.
  • T-034: CP-1 35 мин + CP-F 50 мин; T-035: 37 + 29 мин.
  • Phase 2 review почти весь в T-022 CP-F 48 мин.
∅

Что не объясняет рост

  • Retries: attempts 16 → 15; по 1 на chunk.
  • Число chunk’ов: 16 → 15.
  • Produced-файлы: 38 → 31.
  • Diff volume: U-02 15/583 → 14/583; R-02 13/573 → 5/101, но время выросло.
  • Acceptance checklist: avg 7.5 → 6.6; artifacts avg 4.2 → 4.6 — почти без изменений.

Как читать итог

Нельзя говорить «Phase 3 в 7 раз медленнее всей Phase 2»: Phase 2 total включает T-025..T-028 (I-02/Q-01/Q-02/F-01), которых в Phase 3 ещё нет. Корректная формулировка: на 8 завершённых аналогичных этапах work time вырос в 7.05×, и предпосылки для такого же роста в I-02/Q-01/Q-02 есть (built-frontend, контекст, verification), но их надо измерить после завершения.

Рекомендации

Что делать

  • Дробить cross-cutting S-04-задачи по поверхностям: day view, shared ModelCell, S-01 regression, build/tests — отдельные chunk’и с явными acceptance.
  • Context pack на роль: только релевантные фрагменты requirements/UX/contracts/QA; контролировать input/cache/sessions. Phase 3 R/I — основной кандидат.
  • Раньше делать build/built-frontend проверки: T-037-подобный DOM smoke — в chunk acceptance, а не в конце.
  • Починить chunk-budget: не считать package-lock/сгенерированные SVG как authored output; T-036/T-033 — known check-design gaps.
  • Планировать review windows: отделять work time от calendar; не ставить зависимые этапы на overnight review (T-036 13 ч 37 мин).
  • Писать per-chunk время в ledger: сейчас у многих chunk’ов usage.min=0; без этого анализ остаётся частично оценочным.

Чего не делать

  • Не использовать T-021 / U-02 5 мин как baseline для планирования S-04: это outlier быстрого delta.
  • Не объяснять рост «большим output»: produced и diff в U-02/R-02 не выросли, а время выросло.
  • Не объяснять рост retries: attempts по 1 на chunk в обеих фазах.
  • Не сравнивать полные phase totals до завершения T-037/T-038/T-039.
  • Не оптимизировать только модель/effort: основной рычаг — scope, контекст и verification, а не latency модели.

Оговорки

Ограничения данных

  • Observational comparison: scope S-04 отличается по дизайну; это не controlled experiment.
  • Phase 2 usage n/a для T-018..T-021, T-023; token-сравнение только там, где данные есть.
  • T-021 5 мин — outlier; U-02 ratio 45.8× чувствителен к нему.
  • T-036 diff stat в checkpoint не записан; используем 8 produced files + package-lock 98 KB.
  • T-033 calendar считается от фактического старта 09:53:50: 4 ч 26 мин (4:26:40); 4 ч 50 мин включало 23 мин inter-task idle. Детали: U-02 deep dive.
  • Work time — из activity; calendar — из checkpoint; review — из CP requested/reviewed. Метрики не взаимозаменяемы.
  • Calendar/review в таблицах округлены вниз до минут; точные timestamps — в checkpoint files.
  • T-037 in progress, T-038..T-040 pending; I-02/Q-01/Q-02/D-01 не входят в 8 пар.

Как читать цифры

  • 7.05× — отношение sum(work P3) / sum(work P2) по 8 парам.
  • 10.75× — отношение календарного интервала 8 пар: 4 ч 23 мин → 47 ч 10 мин.
  • 25.53× — отношение review waits: 1 ч 02 мин → 26 ч 25 мин.
  • Review wait может превышать calendar - work из-за округления и разных источников; не складывайте метрики без оговорок.
  • «Прочее / idle» на phase chart — остаток calendar - work - review; включает паузы, переходы и tool/model overhead.
