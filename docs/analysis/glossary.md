## Продуктовые термины

| Термин | Определение |
|---|---|
| **opencode** | AI-агентная среда разработки — исходный источник данных об активностях пользователя. Сервис только читает её данные, не модифицирует и не требует внешних API (C-1, C-3, R-027). |
| **session (сессия opencode)** | Единица работы пользователя в opencode (по recommended default Q-002: 1 сессия = 1 задача). Содержит последовательность сообщений/действий, usage-данные, финальное состояние. |
| **task (задача)** | Отслеживаемая единица в сервисе: что делалось, какие решения предлагались и какое выбрано, чем завершилось (R-002..R-006). Формально: сущность сервиса, связанная с данными opencode. |
| **activity (активность)** | Единичное действие/событие в рамках задачи (обращение к агенту, действие среды) с меткой времени (R-003). |
| **action / step (шаг/действие)** | Конкретная запись действия в рамках задачи; синоним activity в UI (R-003, R-007). |
| **solution / decision (решение)** | Вариант действия/подхода, предложенный в рамках задачи (предложенное решение — R-004) и тот, что выбран (выбранное решение — R-005). |
| **final status / task end state (финальный статус)** | Состояние, которым завершилась задача (завершена/прервана/не завершена — набор фиксируется на R-01) (R-006). |
| **token usage (потребление токенов)** | Объём токенов (вход/выход), потреблённый LLM-моделью при выполнении (R-012). |
| **model (модель)** | Конкретная LLM-модель (например, локальная модель Ollama), по которой разбивается token usage (R-012, R-013). |
| **primary model (основная модель)** | Модель с максимальной суммой input + output + cache tokens по задаче; отображается в S-01 как основная, при нескольких моделях — с видимым индикатором `+N` (R-012, R-014). |
| **models array (список моделей)** | Упорядоченный массив `models` в ответе `GET /api/tasks`: total tokens desc, tie-break по имени модели; пустой массив означает отсутствие usage (R-014). |
| **model column (колонка «Модель»)** | Колонка списка S-01 сразу после «Название»; показывает основную модель и `+N`, полный список — в tooltip и `aria-label`; при отсутствии usage — «Нет данных» (R-014). |
| **day view (дневной вид календаря, S-04)** | Экран `/calendar/:date` с таблицей задач за один день: колонки «Задача», «Модель», «Начало», «Окончание», «Продолжительность», «Статус» (R-008, R-015). |
| **day-view model cell (ячейка модели в S-04)** | Ячейка колонки «Модель» таблицы дневного вида (S-04) сразу после «Задача»; правила идентичны S-01: основная модель и `+N`, полный список — в `title` и `aria-label`, при пустом `models` — «Нет данных» (R-015; термины primary model, `+N`, «Нет данных» — те же, что в S-01, R-014). |
| **duration (продолжительность)** | Длительность задачи: по recommended default (Q-002) — конец − начало сессии (R-009). |
| **calendar view (календарный вид)** | Экран с отображением задач по датам/периодам с навигацией (R-008). |
| **AI search (AI-поиск)** | Поиск задач свободным текстом с обработкой LLM/векторным поиском, а не только точным совпадением (R-010). |
| **result / snippet (результат/сниппет)** | Задача в выдаче поиска с кратким объяснением релевантности (R-011). |

## Harness-термины (процесс)

| Термин | Определение |
|---|---|
| **FR (functional requirement)** | Функциональное требование — что система должна делать; атомарно, с ID `R-NNN` (R-001..R-015). |
| **NFR (non-functional requirement)** | Нефункциональное требование — как система это делает (производительность, безопасность, operability и т.п.); атомарно, с ID `R-NNN` (R-020..R-030). |
| **R-NNN** | Единая нумерация требований FR и NFR в этом проекте (001–019 FR, 020+ NFR), используется в traceability, e2e, QA-матрице. |
| **UC-E2E-NNN (e2e use case)** | Формальный end-to-end сценарий, покрывающий одно или несколько `R-NNN`; определяется на стадии A-02 (T-003) и потребляется e2e-автоматизацией (I-02) и QA (Q-01/Q-02). |
| **dataset (test dataset)** | Машин-читаемый (YAML) контракт тестовых данных для e2e: среда (без секретов), шаги, ожидаемые значения, cleanup; артефакт A-02. |
| **wireframe (макет)** | Низкодетальный рисунок экрана (PlantUML Salt / статичный HTML-прототип), артефакт U-02. |
| **ADR (Architecture Decision Record)** | Запись архитектурного решения с альтернативами и обоснованием; артефакт R-01. |
| **checkpoint (чекпоинт)** | Обязательная остановка процесса для проверки пользователем артефактов (CP-1, CP-2, CP-F); решение пишется в `docs/checkpoints/T-XXX-CP-N.md`. |
| **traceability (прослеживаемость)** | Связка «строка исходных требований → R-NNN → UC-E2E-NNN → тест/QA» (раздел 5 `requirements-*.md`, `docs/qa/e2e-plan-*.md`). |
| **MoSCoW (Must/Should/Could)** | Приоритизация требований, используемая в FR/NFR. |
| **recommended default** | Временное значение по умолчанию для открытого вопроса (Q-NNN), по которому работа продолжается без блокировки до явного решения. |
