## 1. Контекст и цель

Разрабатывается новый локальный сервис (backend Java + Postgres + Redis в Docker, frontend Vue.js/web),
который мониторинг-ит активностей пользователя в opencode (AI-агентная среда разработки) и даёт разработчику
обзор: что делалось в рамках задач, какие решения предлагались и какое выбрано, чем задачи завершились;
календарный вид задач с продолжительностью; поиск задач с использованием ИИ; учёт потреблённых токенов
в разрезе используемых моделей.

Аудитория: локальный разработчик (по умолчанию single-user, см. Q-004).
Сервис работает локально; внешние API не используются (кроме локальной LLM для AI-поиска — Q-007).

## 2. Предположения и ограничения (constraints)

- **C-1** Стек зафиксирован (ИТ:7, ИТ:8): backend — Docker, Java, Postgres, Redis; frontend — Vue.js + web.
  Детализированы как NFR R-020..R-022.
- **C-2** Локальная разработка: весь стек поднимается `docker-compose` одной командой (производится из C-1 и цели локального сервиса).
- **C-3** Сервис не модифицирует opencode: только чтение данных об активностях (инференс из ИТ:1 «мониторинг активностей»).
- **A-1** По умолчанию один пользователь (локальный разработчик) — см. Q-004 (recommended default).
- **A-2** LLM для AI-поиска — локальная (Ollama), внешних API нет — см. Q-007 (recommended default).
- **A-3** Язык интерфейса по умолчанию русский — см. Q-006 (recommended default).

Открытые вопросы, влияющие на трактовку требований, вынесены в
`docs/analysis/questions-ai-task-tracker.md` (Q-001..Q-008). Для продолжения работы без блокировки
приняты recommended defaults; окончательное решение — за пользователем на CP-1 и за архитектором на R-01.

## 3. Функциональные требования (FR)

Приоритеты: Must / Should / Could (MoSCoW). Акцептанс-критерий — проверяемое утверждение,
покрываемое e2e (на A-02) и QA (Q-01/Q-02).

### R-001. Сбор данных об активностях из opencode — Must
- **Описание**: Сервис собирает данные об активностях пользователя в opencode (сессии/сообщения/использование)
  из локальных источников данных opencode, без изменения opencode и без внешних сетей.
- **Источник**: ИТ:1 («сервис мониторинга активностей пользователя в opencode»), ИТ:3.
- **Акцептанс**: при наличии известной сессии opencode данные о ней появляются в хранилище сервиса;
  повторная синхронизация не создаёт дубликатов (idempotency, см. R-025).
- **Зависит от вопросов**: Q-001 (источник/формат данных), Q-002 (задача ↔ сессия).

### R-002. Сущность «задача» и её сохранение — Must
- **Описание**: Сервис идентифицирует «задачи» по данным opencode и хранит их как отдельные сущности:
  уникальный ID, название, время начала/окончания, статус, связь с исходными данными opencode.
- **Источник**: ИТ:3 («отслеживать задачи»).
- **Акцептанс**: каждая отслеживаемая задача отображается отдельной записью с уникальным ID;
  отображение «задача → исходные данные opencode» сохраняется и доступно для аудита.
- **Зависит от вопросов**: Q-002.

### R-003. Действия (шаги) в рамках задачи — Must
- **Описание**: Сервис фиксирует, что делалось в рамках каждой задачи: перечень действий/шагов
  (например, обращения к агенту, действия среды) с временными метками.
- **Источник**: ИТ:3 («что в рамках их делалось»).
- **Акцептанс**: для задачи с зафиксированными в данных действиями все они отображаются в деталях задачи
  в хронологическом порядке с метками времени.
- **Зависит от вопросов**: Q-001, Q-008.

### R-004. Предложенные решения — Must
- **Описание**: Сервис фиксирует решения (варианты), которые предлагались в рамках задачи.
- **Источник**: ИТ:3 («какие решения предлагались»).
- **Акцептанс**: для задачи, в данных которой зафиксированы предложенные решения, они отображаются
  в деталях задачи как варианты.
- **Зависит от вопросов**: Q-008 (формат «решений» в данных opencode).

### R-005. Выбранное решение — Must
- **Описание**: Сервис фиксирует, какое из предложенных решений было выбрано.
- **Источник**: ИТ:3 («что было выбрано»).
- **Акцептанс**: выбранное решение помечено отдельно от остальных предложенных и видно в деталях задачи.
- **Зависит от вопросов**: Q-008.

### R-006. Финальный статус задачи — Must
- **Описание**: Сервис фиксирует, чем завершилась задача (финальный статус из согласованного набора
  значений, напр. завершена/прервана/не завершена — набор фиксируется на R-01 в зависимости от Q-002).
- **Источник**: ИТ:3 («Чем завершилось»).
- **Акцептанс**: каждая завершённая/закрытая задача имеет финальный статус, отображаемый в списке и в деталях.
- **Зависит от вопросов**: Q-002.

### R-007. Просмотр списка задач и деталей задачи в UI — Must
- **Описание**: Пользователь в веб-интерфейсе открывает список задач и страницу деталей задачи:
  действия (R-003), предложенные и выбранное решения (R-004, R-005), финальный статус (R-006),
  продолжительность (R-009), токены по моделям (R-012, R-013).
- **Источник**: ИТ:3, ИТ:4.
- **Акцептанс**: список задач и страница деталей загружаются и отображают актуальные данные для выборки задач.
- **Зависит от вопросов**: Q-006 (язык UI).

### R-008. Календарный вид задач — Must
- **Описание**: Пользователь может видеть задачи на календаре (по датам) с возможностью навигации
  (день/неделя/месяц — точный набор определяет UX на U-01/U-02).
- **Источник**: ИТ:4 («смотреть на календаре эти задачи»).
- **Акцептанс**: задачи отображаются на датах, соответствующих их началу и/или интервалу;
  навигация по календарю изменяет видимый период.
- **Зависит от вопросов**: Q-002 (какой интервал считать «продолжительностью» для календаря).

### R-009. Продолжительность задачи — Must
- **Описание**: Сервис рассчитывает и отображает продолжительность каждой задачи
  (по умолчанию: конец − начало; вариант «суммарное активное время» — решение на Q-002/R-01).
- **Источник**: ИТ:4 («их продолжительность»).
- **Акцептанс**: для задачи с известными метками времени начала/окончания отображённая продолжительность
  совпадает с расчётной (по согласованному правилу) с точностью до единицы измерения времени.
- **Зависит от вопросов**: Q-002.

### R-010. Поиск задач с использованием ИИ — Must
- **Описание**: Пользователь выполняет поиск задач свободным текстом (естественный язык);
  запрос обрабатывается LLM/векторным поиском (AI-поиск), а не только точным совпадением.
- **Источник**: ИТ:4 («находить их по поиску (с использованием ИИ)»).
- **Акцептанс**: для запроса, семантически соответствующего содержимому известной задачи,
  эта задача входит в результат поиска (top-K).
- **Зависит от вопросов**: Q-007 (локальная LLM).

### R-011. Результаты поиска — Should
- **Описание**: Поиск возвращает ранжированный список задач (top-K, K по умолчанию ≥ 5)
  со сниппетом/кратким объяснением релевантности для каждого результата.
- **Источник**: ИТ:4 (поиск).
- **Акцептанс**: результат поиска отображает не менее 5 задач (если они существуют) со сниппетом.
- **Зависит от вопросов**: Q-007.

### R-012. Учёт потребления токенов по моделям — Must
- **Описание**: Сервис фиксирует объём потреблённых токенов в разрезе используемых LLM-моделей
  (входные/выходные токены, модель, время; агрегация по задачам/периодам).
- **Источник**: ИТ:4 («Отслеживать объем потреченных токенов в разрезе используемых моделей»).
- **Акцептанс**: для известного набора сообщений с указанием моделей и объёмов токенов
  агрегированные значения по моделям совпадают с исходными данными.
- **Зависит от вопросов**: Q-003 (источник данных о токенах).

### R-013. Просмотр статистики токенов — Must
- **Описание**: Пользователь видит потребление токенов в разрезе моделей
  (суммарно и/или за выбранный период; точный набор виджетов — UX U-01/U-02).
- **Источник**: ИТ:4 (разрез по моделям).
- **Акцептанс**: экран/виджет токенов отображает разбивку по моделям; выбор периода изменяет отображаемые значения.
- **Зависит от вопросов**: Q-006 (язык UI).

## 4. Нефункциональные требования (NFR)

Категории: performance / reliability / security / usability / operability / compliance / constraint.
Целевые значения с меткой **«to be decided»** подтверждаются пользователем на CP-1 (и уточняются на R-01).

### R-020. Стек backend — constraint, Must
- **Описание**: Backend реализован на Java; первичное хранилище — Postgres; Redis — кэш/очереди;
  работа в контейнере Docker.
- **Источник**: ИТ:7.
- **Акцептанс**: контейнер backend (Java) + Postgres + Redis запускаются из `docker-compose`;
  зависимости соответствуют зафиксированному стеку.

### R-021. Стек frontend — constraint, Must
- **Описание**: Frontend — Vue.js, веб-приложение (браузер).
- **Источник**: ИТ:8.
- **Акцептанс**: UI реализован на Vue.js и доступен через браузер (веб).

### R-022. Локальный запуск стека — operability, Must
- **Описание**: Весь стек (backend, Postgres, Redis, frontend) поднимается одной командой
  `docker compose up` в локальной среде (Windows, PowerShell).
- **Источник**: ИТ:7–8 + C-2.
- **Акцептанс**: из «чистого» состояния одной командой поднимается весь стек, UI доступен в браузере,
  backend отвечает на health-запрос.

### R-023. Производительность (ориентир) — performance, Should
- **Описание**: На локальном окружении: загрузка списка задач (≤ 1000 задач) < 3 с;
  ответ AI-поиска < 15 с. **to be decided** (подтвердить целевые значения).
- **Источник**: ИТ:3–4 (практичная работа со списком и поиском).
- **Акцептанс**: замеры в e2e/QA на локальном окружении в пределах целевых значений.

### R-024. Масштабируемость по объёму данных — performance, Should
- **Описание**: Поддерживается ≥ 12 месяцев данных активностей (десятки тысяч событий)
  без потери читаемости/производительности списков. **to be decided** (конкретный объём).
- **Источник**: ИТ:1–4 (накопление истории).
- **Акцептанс**: на сгенерированном датасете (e2e) списки/поиск работают в пределах R-023.

### R-025. Надёжность хранения — reliability, Must
- **Описание**: Данные не теряются при перезапуске сервиса/БД; повторная синхронизация идемпотентна
  (нет дубликатов); частичные сбои синхронизации не порождают «полу-записей».
- **Источник**: ИТ:3 (отслеживание истории), ИТ:7 (Postgres как хранилище).
- **Акцептанс**: после перезапуска контейнеров данные сохраняются; двойная синхронизация той же сессии
  не создаёт дубликатов задач/событий.

### R-026. Качество данных: полнота и актуальность — performance/data quality, Must
- **Описание**: Полнота: все события из источника, соответствующие согласованному формату, фиксируются.
  Актуальность: задержка от завершения активности в opencode до отображения в сервисе ≤ **5 минут**
  (при poll-режиме; **to be decided** в зависимости от Q-001).
- **Источник**: ИТ:1, ИТ:3.
- **Акцептанс**: e2e-проверка по known dataset: ожидаемые записи присутствуют; задержка в пределах цели.

### R-027. Локальность и безопасность — security, Must
- **Описание**: Работа только в локальной сети; внешние сетевые вызовы запрещены (кроме локальной LLM/Ollama);
  секреты/ключи не хранятся в коде, конфигах и логах; по умолчанию single-user локальный доступ
  (Q-004); минимальный набор логов без разглашения содержимого чужих данных.
- **Источник**: C-1 (локальный сервис), harness-правила локальности (локальные Ollama-модели).
- **Акцептанс**: в конфигурации и сетевых вызовах отсутствуют внешние эндпоинты (кроме localhost/Ollama);
  в кодовой базе и логах отсутствуют секреты (проверка QA).

### R-028. Наблюдаемость — operability, Should
- **Описание**: Структурированные логи backend и frontend; health/readiness-эндпоинты backend;
  видимые пользователю сообщения об ошибках для типовых сбоев (нет Ollama, нет данных opencode).
- **Источник**: ИТ:7 (эксплуатация в Docker).
- **Акцептанс**: health-эндпоинт отвечает; при недоступности источника данных UI показывает явное сообщение,
  а не молча пустой список.

### R-029. Хранение и удаление истории — compliance, Could
- **Описание**: Период хранения данных: **to be decided** (recommended default — хранение без ограничения
  по времени + ручное удаление истории; см. Q-005). Предусмотрен механизм ручного удаления данных.
- **Источник**: ИТ:3–4 (накопление истории).
- **Акцептанс**: существует управляемое удаление данных (ручная операция) с подтверждением.

### R-030. Язык интерфейса — usability, Could
- **Описание**: Язык UI по умолчанию — русский (recommended default, Q-006); локализация других языков
  не требуется в первом релизе.
- **Источник**: ИТ (все формулировки на русском).
- **Акцептанс**: все пользовательские тексты UI на русском языке.
