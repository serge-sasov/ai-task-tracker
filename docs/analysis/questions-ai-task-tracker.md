## Q-001. Источник и формат данных об активностях из opencode — **blocking**

- **Контекст**: Сервис должен собирать «активности пользователя в opencode» (R-001, R-003, R-026).
  Не определено, откуда и в каком виде читаются данные.
- **Варианты**:
  1. Файлы сессий/логов opencode (локальные файлы, парсинг);
  2. SDK/библиотека opencode;
  3. HTTP API локального сервера opencode;
  4. Webhook/события, отправляемые opencode (если поддерживается);
  5. Polling по файлам/API с интервалом.
- **Рекомендуемый default**: чтение из **локальных файлов сессий/логов opencode** (вариант 1) + **polling** с интервалом
  (см. R-026, задержка ≤ 5 минут) — самый автономный, не требующий внешних зависимостей и совместимый с C-1/C-3.
- **Влияние**: формат парсинга и контракт данных (R-01), полнота/актуальность (R-026), e2e-dataset (A-02),
  источник «решений» и «токенов» (Q-003, Q-008).

## Q-002. Что считать «задачей» в opencode и как считать продолжительность — **blocking**

- **Контекст**: R-002 (сущность «задача»), R-006 (финальный статус), R-008/R-009 (календарь, продолжительность), R-025 (без дубликатов).
  Требуется однозначный маппинг «задача ↔ данные opencode» и набор статусов.
- **Варианты**:
  1. 1 задача = 1 сессия opencode;
  2. 1 задача = группа связанных сессий / один «таск» из структуры opencode;
  3. 1 задача = один пользовательский запрос/проброс.
  Продолжительность: (а) конец − начало сессии; (б) сумма активных интервалов.
- **Рекомендуемый default**: **1 задача = 1 сессия opencode** (вариант 1); продолжительность = **конец − начало сессии** (вариант а);
  финальный статус = выведен из состояния/итоговой записи сессии (набор статусов фиксируется на R-01).
- **Влияние**: модель данных и контракты (R-01), календарный вид (R-008), расчёт R-009,
  e2e-определения ожидаемых значений (A-02), идемпотентность R-025.

  Решение: Делаем default

## Q-003. Источник данных о потреблённых токенах по моделям — **non-blocking**

- **Контекст**: R-012 (учёт токенов по моделям). Не определено, где хранится история токенов.
- **Варианты**:
  1. Из полей сессий/сообщений opencode (usage/usage per model);
  2. Из локальных логов/статистики LLM-провайдера (Ollama);
  3. Служебная таблица, заполняемая парсером из (1)/(2).
- **Рекомендуемый default**: **из полей usage сессий/сообщений opencode** (вариант 1), нормализованные
  в отдельную сущность «token_usage» (модель, вход/выход, время, ссылка на задачу).
- **Влияние**: нормализация данных (R-01), агрегация R-012, виджет R-013, e2e-known dataset (A-02).

Решение: Делаем default

## Q-004. Многопользовательский режим или single-user — **non-blocking**

- **Контекст**: R-027 (безопасность), R-030. Сервис «локальный», аудитория — разработчик.
- **Варианты**: 1) single-user локальный (без аутентификации); 2) несколько пользователей + аутентификация/изоляция.
- **Рекомендуемый default**: **single-user локальный** (без встроенной аутентификации, доступ по localhost);
  многопользовательский режим — вне скоупа первого релиза.
- **Влияние**: R-027 (упрощение безопасности), R-01 (отсутствие auth-контрактов), UX (U-01/U-02).

Решение: Делаем default

## Q-005. Период хранения данных (retention) — **non-blocking**

- **Контекст**: R-024 (масштаб), R-029 (хранение/удаление), R-026 (полнота).
- **Варианты**: 1) хранение без ограничения по времени; 2) фиксированный retention (например, N месяцев) + авто-чистка;
  3) ручной выбор периодов удаления.
- **Рекомендуемый default**: **хранение без ограничения по времени** + **ручное удаление истории** (R-029) +
  авто-архивация/агрегация для масштаба (R-024); авто-чистка — не требуется в первом релизе.
- **Влияние**: R-024/R-029, миграции Postgres (R-01), e2e-объём данных (A-02/I-02).

Решение: Делаем default

## Q-006. Язык интерфейса — **non-blocking**

- **Контекст**: R-030, R-007/R-013 (UI-тексты). Исходные требования на русском.
- **Варианты**: 1) только русский; 2) русский + английский (i18n); 3) авто по локации браузера.
- **Рекомендуемый default**: **только русский** в первом релизе (R-030); i18n — не требуется.
- **Влияние**: R-030, UX-копирайт (U-02), e2e-проверки текстов (A-02).

Решение: Делаем default

## Q-007. Конкретная LLM для AI-поиска и её локальность — **non-blocking**

- **Контекст**: R-010 (AI-поиск), R-011 (результаты), R-027 (локальность, без внешних API).
- **Варианты**:
  1. Локальная LLM через Ollama (embedding + LLM-ранжирование);
  2. Внешний API LLM (нарушает C-1/R-027 — отвергаем);
  3. Только локальный семантический/векторный поиск без LLM-перефразирования.
- **Рекомендуемый default**: **локальная LLM через Ollama** (embedding-модель + LLM-ранжирование/ответ),
  работа только с localhost; модель и размер контекста фиксируются на R-01 с учётом доступных локальных моделей.
- **Влияние**: R-010/R-011, контракт backend↔LLM (R-01), e2e-dataset и runner (A-02/I-02), R-027 (без внешних вызовов).

Решение: Делаем default

## Q-008. Формат «решений» (предложено/выбрано) в данных opencode — **blocking**

- **Контекст**: R-004 (предложенные решения), R-005 (выбранное решение). Не определено, как в данных opencode
  выглядят «предложенные варианты» и «выбранный вариант».
- **Варианты**:
  1. Отдельные структурированные поля/сущности в сессии (решение/варианты);
  2. Разметка в тексте сообщений (парсинг по паттернам/LLM-извлечение);
  3. Отсутствует в данных → вывод по правилам (не рекомендуется).
- **Рекомендуемый default**: **извлечение LLM-ом из контекста сессии** (вариант 2) с сохранением ссылок на исходные
  сообщения для аудита; если в данных есть структурированные поля (вариант 1) — предпочесть их.
- **Влияние**: R-004/R-005, e2e-known dataset (A-02), контракт данных (R-01), качество данных R-026.

Решение: Делаем default
