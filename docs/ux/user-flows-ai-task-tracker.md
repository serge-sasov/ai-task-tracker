## 1. Персоны

### P-1 — Локальный разработчик (основная персона)

- **Кто**: разработчик, работающий в opencode (AI-агентная среда); использует сервис только на своей машине (Q-004, single-user).
- **Цель**: понять, что делалось в рамках задач, какие решения предлагались/выбраны, чем задачи завершились; видеть задачи на календаре с продолжительностью; находить задачи свободным текстом (AI-поиск); контролировать потребление токенов по моделям (ИТ:3–4; R-003..R-013).
- **Контекст**: работает в браузере на localhost; стек поднят `docker compose up` одной командой (R-022); нет аутентификации (Q-004); язык интерфейса — русский (Q-006).
- **Боли без сервиса**: история активностей в opencode не агрегирована; нет обзора решений и токенов; трудно ответить «что и как долго делалось по задаче X».
- **Ключевые сценарии**: просмотр списка/деталей задач (UC-E2E-003), календарь (UC-E2E-005), AI-поиск (UC-E2E-004), статистика токенов (UC-E2E-006), удаление истории (UC-E2E-008).

### P-2 — Наблюдатель / QA (вторичная персона)

- **Кто**: тот же разработчик в роли проверяющего (e2e-раннер, QA-инженер); не является отдельным пользователем системы (single-user — Q-004).
- **Цель**: убедиться, что стек поднимается, данные импортируются без дублей, UI корректно показывает пустые/ошибочные состояния (R-028).
- **Ключевые сценарии**: стартовое состояние (UC-E2E-001), надёжность/идемпотентность (UC-E2E-007).
- **UX-влияние**: определяет обязательные состояния UI: «нет данных» (пусто), «источник недоступен» (ошибка), «AI-поиск недоступен» (ошибка) — явные сообщения на русском, а не белые страницы (R-028, UC-E2E-001 S4, UC-E2E-004 E1).

## 2. Информационная архитектура и навигация

### Структура навигации

Одностраничное Vue.js-приложение (R-021) с левой боковой навигацией (5 пунктов) и строкой AI-поиска в шапке. Все разделы доступны без аутентификации (Q-004):

| № | Пункт меню (RU) | Экран | Назначение |
|---|---|---|---|
| 1 | «Задачи» | S-01 | Список задач → S-02 |
| 2 | «Поиск» | S-03 | AI-поиск задач свободным текстом |
| 3 | «Календарь» | S-04 | Задачи по датам, режимы День/Неделя/Месяц/Год |
| 4 | «Токены» | S-05 | Потребление токенов в разрезе моделей |
| 5 | «Управление данными» | S-06 | Удаление истории (с подтверждением) |

Глубина вложенности: 1 уровень для разделов, 1 переход вглубь (S-01 → S-02). Из S-02 возврат — кнопка «Назад к списку» + кнопка «Назад» браузера (history API). Клик по задаче в S-03/S-04 приводит на S-02 той же задачи.

### Иерархия данных (влияет на IA)

- **Задача** (1 задача = 1 сессия opencode, Q-002) — базовая единица во всех разделах: список, календарь, результаты поиска.
- Внутри задачи: **действия** (хронология, R-003), **решения** (предложенные + выбранное, R-004/R-005), **токены по моделям** (R-012), **продолжительность** (конец − начало, R-009).
- **Статистика токенов** — агрегированный вид по моделям за период (R-013), отдельный раздел, не встроен в список.
- **Управление данными** — служебный раздел (R-029), отделён от рабочих разделов.

### Принципы

1. **Один вход на каждую сущность**: к задаче можно попасть из списка, календаря или поиска — всегда на один и тот же экран S-02.
2. **Пустые состояния обязательны**: каждый раздел имеет явное состояние «нет данных» на русском (R-028; UC-E2E-001 S4).
3. **Только чтение** (кроме S-06): пользователь не редактирует задачи — данные приходят из opencode (C-3).
4. **Статус задачи** — цветовая метка + текст (Завершена / Прервана / Не завершена — набор фиксируется на R-01, Q-002).

## 3. Пользовательские потоки

Схема потока: `Экран → действие пользователя → результат/следующий экран`. Каждый поток связан с UC-E2E и R-NNN.

### F-1. Просмотр списка задач и деталей задачи

- **Путь**: S-01 → S-02.
- **Шаги**:
  1. Пользователь открывает UI (после `docker compose up`) → по умолчанию S-01 «Задачи» (UC-E2E-003 S1).
  2. В списке видит карточки/строки задач: название, модель, дата начала, продолжительность, статус (RU-тексты, R-030; продолжительности по правилу конец−начало, R-009; колонка «Модель» сразу после названия, R-014; UC-E2E-003 S2/S8). Для задачи с usage нескольких моделей видна основная модель и `+N`, полный список — в tooltip/`aria-label`; без usage — «Нет данных».
  3. Кликает по задаче → S-02 «Детали задачи»: действия в хронологическом порядке с метками времени (R-003), решения: предложенные + выбранное выделено (R-004/R-005), блок токенов по моделям (R-012; UC-E2E-003 S3–S7).
  4. Кнопка «Назад к списку» → возврат на S-01 (состояние списка сохраняется: прокрутка/страница).
- **Альтернатива**: задачи, у которых решений не было (TASK-004/TASK-005) → S-02 показывает явное состояние «Решений не зафиксировано» (UC-E2E-003 S7).
- **Ошибки**: сбой API деталей → сообщение на русском + кнопка «Повторить», список остаётся доступен (R-028; UC-E2E-003 E1).
- **Связь**: UC-E2E-003; R-002, R-003, R-004, R-005, R-006, R-007, R-009, R-014, R-030.

### F-2. AI-поиск задач свободным текстом

- **Путь**: шапка (строка поиска) → S-03.
- **Шаги**:
  1. Пользователь вводит запрос свободным текстом (напр., «настройка CI для репозитория») → нажимает «Найти»/Enter (UC-E2E-004 S1).
  2. Индикатор поиска (LLM отвечает до 15 с, R-023).
  3. S-03 «Результаты поиска»: ранжированный список (top-K ≥ 5) со сниппетом/объяснением релевантности для каждой задачи (R-011; UC-E2E-004 S1–S3).
  4. Клик по результату → S-02 деталей (общий путь с F-1).
- **Альтернатива**: нерелевантный запрос («рецепт борща») → честная пустая выдача «Ничего не найдено», без выдуманных совпадений (UC-E2E-004 S4).
- **Ошибки**: пустой запрос → валидация: «Найти» неактивна / «Введите запрос» (UC-E2E-004 E2); Ollama недоступна → «AI-поиск недоступен (LLM не отвечает)» + возможность вернуться к списку, приложение не падает (R-028; UC-E2E-004 E1).
- **Связь**: UC-E2E-004; R-010, R-011, R-023, R-027, R-028.

### F-3. Календарный вид задач с продолжительностью

- **Путь**: S-04 → S-02.
- **Шаги**:
  1. Пользователь открывает «Календарь» → режим по умолчанию «Неделя» (набор режимов День/Неделя/Месяц/Год определён UX-ом, R-008; UC-E2E-005 S1).
  2. Задачи отображаются на датах начала с продолжительностью (R-008/R-009); дни без задач — пустые, но видимые.
  3. Переключение режимов День/Неделя/Месяц/Год и навигация назад/вперёд по периоду (UC-E2E-005 S2–S4); пустой период — явное пустое состояние, не ошибка.
  4. Режим «Месяц» — полная сетка месяца по неделям (Пн–Вс): все дни месяца + приглушённые дни смежных (неактивны); задачи с продолжительностью в своих днях.
  5. Режим «Год» — 12 месяцев со статистикой (задачи/продолжительность/токены); месяцы без данных — «Нет данных».
  6. Клик по задаче → S-02 деталей (UC-E2E-005 S5).
- **Альтернатива**: задача, пересекающая два дня (профиль large) → полоса на обоих днях без дублей записей (UC-E2E-005 A1).
- **Ошибки**: сбой API календаря → сообщение на русском + «Повторить», без устаревших данных (R-028; UC-E2E-005 E1).
- **Связь**: UC-E2E-005; R-008, R-009, R-023, R-030.

### F-4. Статистика потреблённых токенов по моделям

- **Путь**: S-05 (опционально → S-02).
- **Шаги**:
  1. Пользователь открывает «Токены» → S-05 со сводкой за период «Всё время»: разбивка по моделям (вход/выход/итого) + общий итог (R-012/R-013; UC-E2E-006 S1).
  2. Выбирает период (день/диапазон) → значения пересчитываются (UC-E2E-006 S2–S4).
  3. Опционально: переход к задаче из детализации → S-02 с блоком «Токены» по этой задаче (UC-E2E-006 S5).
- **Альтернатива**: модель не использовалась в выбранном периоде → строка с нулями или пометка «нет данных за период», не сломанный виджет (UC-E2E-006 A1).
- **Ошибки**: сбой агрегации → сообщение на русском + «Повторить»; сессия без usage (TASK-002) не искажает суммы (UC-E2E-006 E1–E2).
- **Связь**: UC-E2E-006; R-012, R-013, R-023, R-030.

### F-5. Стартовое состояние (пустой сервис)

- **Путь**: S-01..S-05 в пустом состоянии.
- **Шаги**:
  1. Пользователь открывает UI впервые (стек поднят, данные ещё не собраны) → S-01 показывает явное состояние «нет данных» на русском, а не белую страницу (UC-E2E-001 S4; R-028).
  2. Разделы S-03..S-05 в пустом состоянии: «Ничего не найдено» / «нет данных за период» / пустые периоды (не сломанные экраны; UC-E2E-008 S4).
  3. Служебная подсказка (опционально): «Данные будут импортированы автоматически после синхронизации» — информационный баннер на S-01, без действий пользователя (связь с F-7).
- **Связь**: UC-E2E-001; R-021, R-027, R-028, R-030.

### F-6. Ручное удаление истории

- **Путь**: S-06 → диалог подтверждения → все разделы в пустом состоянии.
- **Шаги**:
  1. Пользователь открывает «Управление данными» → S-06: кнопка «Удалить историю» + предупреждение о необратимости (RU-тексты; UC-E2E-008 S1; R-029/R-030).
  2. Нажатие кнопки → диалог подтверждения (явное подтверждение обязательно, R-029).
  3. «Отмена» → данные не изменяются (UC-E2E-008 A2).
  4. «Подтвердить» → операция удаления; UI показывает успешность; все разделы переходят в корректные пустые состояния (S-01 «нет данных», S-05 нулевые значения, S-04 пустые периоды, S-03 «ничего не найдено» — UC-E2E-008 S3–S4).
- **Ошибки**: сбой удаления → явное сообщение об ошибке; состояние «полудаления» недопустимо (UC-E2E-008 E1); повторное удаление при пустой БД — no-op «данных для удаления нет» (UC-E2E-008 E2).
- **Примечание**: источник opencode не затрагивается (C-3); повторная синхронизация может импортировать данные заново (UC-E2E-008 A1).
- **Связь**: UC-E2E-008; R-028, R-029, R-030.

### F-7. Синхронизация данных (фон, наблюдение в UI)

- **Путь**: фоновый polling-цикл → обновление S-01..S-05 (без прямого действия пользователя).
- **Шаги**:
  1. Сервис читает локальные файлы сессий opencode с интервалом ≤ 5 мин (Q-001; R-026).
  2. После цикла новые/обновлённые задачи видны в S-01/S-04/S-05; UI актуализируется (polling UI или перезагрузка раздела).
  3. Повторная синхронизация идемпотентна: дублей задач/шагов/токенов нет (R-025; UC-E2E-007).
- **Ошибки**: каталог данных недоступен → явное сообщение «источник данных недоступен» (баннер/состояние на S-01), а не молчаливый пустой список (R-028; UC-E2E-002 E1).
- **Связь**: UC-E2E-002, UC-E2E-007; R-001, R-002, R-006, R-025, R-026, R-028.

### F-8. Подъём стека (контекст UX)

- **Путь**: terminal → UI (первый экран S-01).
- **Шаги**:
  1. Пользователь выполняет `docker compose up` → контейнеры backend/postgres/redis/frontend подняты (R-022; UC-E2E-001 S1–S2).
  2. Открывает UI в браузере → Vue.js-приложение загружается без ошибок (R-021; UC-E2E-001 S3).
  3. Внешних сетевых вызовов нет (кроме Ollama на localhost) — UI не требует внешних ресурсов (R-027).
- **Ошибки**: Docker недоступен / health 5xx — сценарий раннера, не UI; в UI проявляется как «источник данных недоступен» (F-7, ошибки).
- **Связь**: UC-E2E-001; R-020, R-021, R-022, R-027.

## 4. Фоновые потоки (без прямого UI)

### BF-1. Polling-цикл (сбор данных)

- **Триггер**: таймер, интервал ≤ 5 мин (Q-001; R-026).
- **Шаги**: backend читает локальные файлы сессий opencode → парсит (задачи, действия, решения, токены) → идемпотентный upsert (без дублей, R-025) → данные доступны UI.
- **Результат в UI**: S-01/S-04/S-05 обновляются (polling UI или перезагрузка раздела); пользователь не выполняет ручных действий (см. F-7).
- **Ошибки**: файлы недоступны → баннер «источник данных недоступен» на S-01 (R-028; UC-E2E-002 E1).

### BF-2. LLM-вызов для поиска (фон)

- **Триггер**: пользовательское действие на S-03 (F-2), затем backend→Ollama.
- **Шаги**: backend отправляет запрос + контекст (корпус задач) локальному Ollama (localhost, R-027) → LLM возвращает top-K ранжирование с обоснованием (R-011) → frontend рендерит S-03.
- **Таймаут**: ≤ 15 с (R-023); после таймаута → состояние ошибки «AI-поиск недоступен» (UC-E2E-004 E1).
- **Примечание**: внешних сетевых вызовов нет — Ollama локальная (Q-007, R-027).
